# Заметки разработки dockfw

Решения, отклонения от ТЗ и найденные нюансы. Каждый пункт: что, почему, как сделано.

## Решения по неоднозначностям ТЗ

Владелец попросил решать технические вопросы самостоятельно. Везде, где был выбор, взят вариант «в сторону закрыто», если он не ломает пример из §3.

1. **`fw.inbound` без протокола = tcp+udp.** Ячейка таблицы §3 обрезана (`` `CIDR `` и дальше съел markdown-pipe). Примеры противоречат: в §4 `192.168.1.0/24:8787` даёт только tcp, а `any:54890` даёт tcp+udp. Выбрано «оба протокола», иначе пример qbittorrent (`any:54890` при публикации 54890/tcp и 54890/udp) не работает. Суффикс `/tcp` или `/udp` сужает. Формат: `<CIDR|адрес|any>:<порт>[/tcp|/udp]`.
2. **`FW_UNLABELED` по умолчанию `ignore`** (§8), в `docker-compose.example.yml` стоит `deny` (§10). Противоречия нет: дефолт кода безопасен для первого запуска, пример показывает рекомендуемый режим.
3. **Симметрия открывает все порты** (как в §3). Порт в ссылке (`qbittorrent:8787`) не добавлен: это изменение схемы labels.
4. **IPv6 закрыт целиком.** В §4 правило `ip6 daddr {fc00::/7, fe80::/10} reject; accept` при `fw.allow.internet` фактически открывает публичный IPv6, а пункт про IPv6 там же говорит «исходящее закрыто целиком». Выбрано «закрыто»: в `output` IPv6 отклоняется сразу после `lo` и `established`, в `input` тоже ничего не открывается, кроме `any:` правил из `fw.inbound` (они без адреса и покрывают оба семейства, как в примере §4).
5. **«Заперт полностью» = как контейнер без `allow.*` и `inbound`.** Так сформулировано в §3. Значит, симметрия от других (корректных) контейнеров к запертому продолжает работать: если у A `fw.allow.containers: B`, а у B кривой label, A всё равно достучится до B. Наоборот, запертый контейнер сам никому симметрию не даёт. То же для контейнеров без labels при `FW_UNLABELED=deny`.
6. **Неизвестный label с префиксом** (`fw.allow.domain` — опечатка) считается невалидным: контейнер запирается и пишется `error`. Молча проигнорированная опечатка означала бы неожиданно закрытый контейнер без объяснения.
7. **`fw.*` labels без `fw.enable: true`** — контейнер не трогается (так в §3), но пишется `warn`.
8. **`fw.enable` с мусорным значением** (`yes`) — контейнер считается включённым и запирается. Опечатка в opt-in не должна выключать защиту.
9. **`fw.allow.cidrs` и источник в `fw.inbound` принимают голый адрес** (`192.168.1.5` = `/32`). Неканонические префиксы (`10.8.0.7/24`) приводятся к сети (`10.8.0.0/24`). IPv6 в этих labels — ошибка валидации (в v1 наборы только IPv4).
10. **Пустые элементы списков** (`a,,b`, хвостовая запятая) пропускаются: это не значение, а форматирование.
11. **Ссылки `project/service` и голый `service` матчат все реплики** сервиса (`deploy.replicas`, `--scale`). Неоднозначность (§6) — только когда голое имя сервиса встречается в нескольких проектах.

## Невозможное или противоречивое в ТЗ

### Wildcard-домены (`*.tmdb.org`)

DNS не умеет перечислять поддомены, а резолвер работает по IP. Резолвить `*.tmdb.org` нечем. Варианты:

- резолвить апекс `tmdb.org` — даёт не то, что просили, и шире запроса;
- DNS-прокси, который видит запросы приложения и добавляет ответы в set, — отдельная большая подсистема (v2);
- принять синтаксис, ничего не резолвить, писать `warn`.

Сделан третий вариант (консервативный): синтаксис из §3 сохранён, label валиден, но на каждом построении policy пишется `warn` с советом перечислить точные имена. Предложение для v2: DNS-прокси на `127.0.0.11` в netns контейнера (перехват ответов Docker DNS и наполнение `domains4` по факту запросов).

## Зависимости

- **`github.com/moby/moby/client` вместо `github.com/docker/docker/client`.** Модуль `docker/docker` заморожен на v28.5.2 (`+incompatible`), клиент Docker теперь развивается как `moby/moby/client`. API тот же (`ContainerList`, `ContainerInspect`, `Events`), поддерживает `DOCKER_HOST` через `client.FromEnv`.
- **Go 1.27**, а не 1.22: актуальные `moby/moby/client` и `google/nftables` требуют свежий toolchain, 1.22 давно без поддержки.
- **`google/nftables` собирается только под Linux** (`golang.org/x/sys/unix` без `NFPROTO_*` на darwin). Поэтому `make test` на macOS гоняет тесты в контейнере `golang:1.27`, а `make lint` использует `GOOS=linux`.

## Проверка `google/nftables` в чужом netns (шаг 3)

Проверено на Docker Desktop (linux/arm64, ядро 6.10): `alpine sleep inf` в пользовательской сети, тест `internal/nft/live_linux_test.go` запущен в контейнере ровно с правами из §10 (`--pid host --network none --read-only --cap-drop ALL --cap-add NET_ADMIN,SYS_ADMIN,SYS_PTRACE --security-opt no-new-privileges`). Затем с хоста `nsenter -t <pid> -n nft list ruleset`.

Результат: работает как описано в ТЗ, обходов не понадобилось. Нюансы:

- **`WithNetNSFd(fd)` сам делает `setns`.** `mdlayher/netlink` открывает netlink-сокет на залоченном потоке внутри netns. Fd 0 библиотека понимает как «текущий netns», поэтому `nft.Apply` отказывается от fd ≤ 0.
- **Атомарная замена таблицы:** в одном batch `add table` (без `NLM_F_EXCL`, на существующей таблице ничего не делает) → `delete table` → `add table` + наборы, цепочки, правила. Так `delete` никогда не падает на отсутствующей таблице, а замена остаётся одной транзакцией.
- **Глобальный счётчик ID наборов.** `nftables.AddSet` берёт ID из глобальной переменной без синхронизации, если `Set.ID == 0`. При параллельном применении в разные netns это гонка данных. Поэтому ID наборов задаются явно (1..n в пределах batch), и `Lookup` ссылается на них.
- **Интервальные наборы:** хватает пар «начало / конец+1 с `IntervalEnd`», ведущий элемент `0.0.0.0` не нужен; `nft list` показывает `10.8.0.0/24, 192.168.1.5`. Пересекающиеся и смежные префиксы сливаются заранее, иначе ядро отвергает batch.
- **NAT Docker DNS не тронут:** до и после применения `table ip nat` (`DOCKER_OUTPUT`, `DOCKER_POSTROUTING`) идентична, `nslookup` из контейнера работает. Наш `oif "lo" accept` пропускает DNAT на 127.0.0.11.
- **`reject with icmpx admin-prohibited` в `output` работает** для локально созданных пакетов. TCP-клиент получает `Host is unreachable` примерно через 1 с (ядро считает ICMP в `SYN_SENT` «мягкой» ошибкой и сообщает её после первого ретрансмита), а не через 2 минуты, как при `drop`. Можно было бы добавить `tcp reset` для мгновенного `ECONNREFUSED`, но это меняет правила §4. Оставлено как в ТЗ.
- **Защита хоста:** `netns.Guard` открывает `/proc/1/ns/net` (с `pid: host` это netns хоста) и собственный netns демона и сравнивает dev:inode любого открываемого netns с ними. Совпадение → отказ до любого `setns`/netlink. PID ≤ 1 отвергается сразу.
- **Поток после `setns` не возвращается в планировщик.** Для кода, который должен выполниться внутри netns (резолвер), используется отдельная горутина с `LockOSThread` без `UnlockOSThread`: поток умирает вместе с горутиной, восстанавливать netns не нужно и ошибиться нельзя.
- **IPv6 в `output`** закрыт правилом `meta nfproto ipv6 reject` сразу после `established` (см. решение 4 выше).

## Демон (шаг 4)

- **Подписка на события до полного прохода.** Сначала `Events`, затем `ContainerList` + `ContainerInspect`, затем обработка событий. Так ничего не теряется между проходом и подпиской. При обрыве потока событий — повторная подписка с backoff (1 с … 30 с) и снова полный проход.
- **Кроме `start`/`die` слушаются `network connect/disconnect`.** `docker network connect` меняет IP контейнера без `start`, и без этого peers соседей устаревали бы до reconcile.
- **Пересчёт зависимых — по факту, а не по графу ссылок.** На каждое событие строятся policy всех известных контейнеров (чистая функция, на 30 контейнерах это микросекунды) и в очередь ставятся те, у кого хэш изменился. Это проще и надёжнее, чем вычислять «кто на кого ссылается» с учётом реплик и неоднозначностей.
- **Найденная гонка:** `b` перезапускается, `die` ставит в очередь пересборку `a` без `b`, и пока она в полёте, приходит `start` для `b`. Сравнение «желаемый хэш против применённого» видело ещё старый применённый хэш (с `b`) и ничего не ставило в очередь. `a` оставался без `b` до reconcile. Исправлено полем `requested`: в очередь ставится всё, где желаемый хэш отличается от применённого *или* от последнего запрошенного. Регрессионный тест `TestEventDuringInFlightApply`.
- **Очередь с ключом по контейнеру:** один контейнер никогда не обрабатывается двумя воркерами (4 воркера), повторные запросы склеиваются, а запрос, пришедший во время обработки, выполняется сразу после неё.
- **Подмена PID.** Netns открывается по `/proc/<pid>/ns/net`, *после* открытия ещё раз делается `inspect`: если контейнер ещё работает с тем же PID, открытый fd точно указывает на его netns (fd держит netns, даже если PID потом переиспользуют). Иначе применение тихо отменяется: событие нового экземпляра обработает его само.
- **`network_mode: container:<id>`** пропускается с warning, как и `host`: такой контейнер живёт в чужом netns, правила там задаёт владелец netns. Применять туда вторую политику значило бы перезаписать чужую таблицу.
- **`nf_log_all_netns` не проверить.** Этот sysctl существует только в netns хоста, а демон работает с `network_mode: none` и в netns хоста входить не должен. При старте пишется `info` с подсказкой вместо проверки.
- **Откат на `drop`.** Если транзакция с `reject with icmpx` не проходит, а та же транзакция с `drop` проходит, демон один раз пишет warning и дальше для всех контейнеров использует `drop`.
- **Окно на старте контейнера.** Между стартом процесса и применением правил проходят миллисекунды: Docker шлёт `start` после запуска процесса. В smoke-тесте на Docker Desktop правила стояли через 10–15 мс после события. Закрыть окно полностью без хуков в runtime нельзя; граница v1, как и «демон остановлен — новые контейнеры без правил» (§5).

## Резолвер (шаг 5)

- **Свой DNS-клиент вместо `net.Resolver`.** ТЗ требует таймаут элемента `max(TTL × 2, 5 мин)`, а `net.Resolver` TTL не возвращает. Запросы A собираются и разбираются через `golang.org/x/net/dns/dnsmessage`. Это не новая зависимость по сути: `golang.org/x/net` уже в графе через клиент Docker, а `dnsmessage` — тот же парсер, что внутри стандартного `net`. При флаге TC повтор идёт по TCP.
- **Сокет создаётся в netns контейнера.** `netns.Guard.Do` переключает выделенный поток в netns контейнера, внутри только `net.Dial("udp", "127.0.0.11:53")`. Сокет остаётся в том netns, а дальнейший ввод-вывод идёт на обычных горутинах. Запрос проходит через DNAT Docker на встроенный DNS ровно так же, как у приложения. Проверено вживую: `example.com` разрешается и открывается, `1.1.1.1` и `github.com` отклоняются.
- **Обновление набора `domains4` — пересборкой всей таблицы,** а не `add element`. Повторный `add element` на существующий элемент в ядрах до ~6.10 не продлевает его timeout, а `delete` + `add` в одном batch падает, если элемента нет. Атомарная пересборка таблицы (той же транзакцией, что и обычное применение) обновляет таймауты всех элементов и не создаёт окна без доменов. Источник правды — кэш резолвера (адрес → срок действия). Срок только продлевается и никогда не сокращается. Ядерный timeout = оставшийся срок, так что если демон умер, адреса сами истекают (fail-closed).
- **Ограничение: IP, которые видит приложение, могут отличаться.** Встроенный DNS Docker не кэширует и пересылает запросы наверх, поэтому CDN может ответить приложению и резолверу разными адресами. Набор копит все адреса за последние `max(TTL × 2, 5 мин)`, это сглаживает ротацию, но не гарантирует попадание. Надёжное решение — тот же DNS-прокси из раздела про wildcard (v2).
- **Только A-записи** (IPv4), как и весь v1.
- Немедленный резолв после `start` (§5, шаг 6) идёт через канал `resolveNow`: таблица сначала ставится без доменов, а через время резолва (на Docker Desktop 30–2500 мс, NXDOMAIN медленнее) пересобирается с ними.
